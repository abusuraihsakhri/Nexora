An operating system that understands AI work.

Nexora — Neural EXecution Orchestration and Resource Architecture — is a research operating-system project investigating what changes when tensors, computation graphs, model state, topology, deadlines and accelerator requirements become visible to the system itself.

01 · Thesis

The OS currently sees less than the workload knows.

AI runtimes know that a tensor is temporary, that a KV cache should remain resident, that one operation depends on another, that a transfer crosses a slow topology edge, or that a request carries a latency deadline. A conventional kernel typically receives only lower-level effects of that knowledge: allocations, mappings, threads, files and device calls.

Conventional view
01

Processes and threads are scheduled without direct knowledge of model graphs or tensor dependencies.

02

Virtual pages do not inherently reveal whether data is transient activation memory, persistent weights or reusable model state.

03

Devices expose queues and memory, while higher-level placement intent remains largely outside the OS policy loop.

Nexora hypothesis
01

Semantic objects make AI-specific intent explicit without replacing the low-level kernel mechanisms beneath them.

02

Graph and lifetime visibility may allow earlier reclamation, better placement and clearer admission decisions.

03

Topology-aware scheduling may account for transfer cost and state locality instead of treating all runnable work as equivalent.

The important constraint: Nexora is not framed as “Linux, but AI.” The research question is narrower: which AI semantics are valuable enough to become OS-visible, and can that visibility measurably improve resource management without moving entire frameworks into the kernel?
02 · Primitives

Eight objects define the semantic plane.

These are architectural concepts, not marketing categories. Each primitive exists to expose information that a resource manager could plausibly use for memory, scheduling, placement, isolation or state-management decisions.

01 / NXTENSOR

NXTensor

Shape, dtype, size, location, mutability, expected lifetime and reuse information for AI data objects.

02 / NXWORK

NXWork

A schedulable operation carrying inputs, outputs, priority, deadline and eligible-resource constraints.

03 / NXGRAPH

NXGraph

Dependencies, readiness and execution structure expressed as a graph rather than inferred from opaque application behavior.

04 / NXSTATE

NXState

Long-lived model resources such as weights, KV caches, adapters, compiled artifacts and session state.

05 / NXRESOURCE

NXResource

A uniform resource description spanning CPUs, accelerators, memory tiers, storage and network-capable devices.

06 / NXTOPOLOGY

NXTopology

NUMA distance, PCIe hierarchy, bandwidth and other locality relationships that change movement cost.

07 / NXCAPABILITY

NXCapability

Explicit authority over resources and objects, with delegation permitted only when lifetime accounting is correct.

08 / NXSCHEDULER

NXScheduler

Policy that can consider dependency readiness, deadlines, queue delay, transfer cost, memory pressure and locality.

03 · Architecture

Semantics above mechanisms, not instead of them.

Nexora keeps the conventional kernel responsibilities—privilege, memory protection, interrupt handling, physical allocation, syscalls and device mechanisms—separate from the experimental AI semantic layer. That separation is essential because it makes the research claim falsifiable: the semantic plane should earn its complexity through measurable policy improvements.

Layer 05

Applications and agents

Inference services, model hosts, agent systems and scientific workloads express goals through existing frameworks and Nexora-aware adapters.

Layer 04

Framework/runtime adapters

PyTorch, JAX, serving systems and compiler runtimes remain outside the kernel while exposing selected semantics through a stable interface.

Layer 03

Nexora semantic plane

NXTensor, NXWork, NXGraph, NXState, NXTopology and NXCapability provide the policy-relevant vocabulary.

Layer 02

Kernel mechanism plane

Privilege boundaries, address spaces, frame/slab allocation, syscalls, exceptions, timers and device-control primitives enforce the decisions.

Layer 01

Heterogeneous hardware

CPU, accelerator memory, GPU/NPU-class compute, storage, fabric and topology form the physical substrate.

04 · Status

What exists today, and what does not.

The repository is deliberately explicit about implementation maturity. Historical phase directories document development steps, but only Phase 14 is presently treated as the full integrated kernel baseline. Later phases are independently validated adjunct packages until their code is migrated into a unified kernel tree.

Phases 01–14
Integrated lineage

Boot, allocators, AI object metadata/work graph, GDT/TSS/IDT, syscall entry, ELF64 validation and host-side integration tests. Phase 14 is the current complete kernel snapshot.

Phase 15
Benchmark package

JSONL benchmark events, summaries and threshold-defined regression checks. It is measurement infrastructure, not a kernel feature by itself.

Phase 16
Validation package

Telemetry, deterministic fault injection and release-health concepts. CI validates this package independently.

Phase 17
Release package

Health, tracing, watchdog and release-gate mechanisms. Manifest verification and concurrency behavior were hardened during the repository audit.

Phase 08
Repository gap

No Phase 8 directory or recoverable archive exists in the repository or accessible project file history. The gap is documented rather than reconstructed from assumptions.

VALIDATED

Kernel link + host tests

The repository CI compiles the freestanding kernel and executes Phase 14 host-side verification from the current source tree.

FAIL-CLOSED

Unsafe mechanisms disabled

Capability delegation and userspace tensor mapping are not pretended to work before real object lifetime and VM-backed mapping exist.

SCOPE

Uniprocessor prototype

The kernel is explicitly treated as single-core until AP startup, per-CPU state and synchronization are engineered end-to-end.

06 · Research

Five hypotheses worth measuring.

The architecture is useful only if it changes measurable system behavior. Nexora therefore treats the following as experiments, not as claims already proven by the current prototype.

H1 / MEMORY

Semantic tensor lifetime

Can explicit producer/consumer lifetime knowledge reduce peak memory and allocator pressure compared with lifetime-blind allocation?

H2 / LOCALITY

Topology-aware placement

Can placement informed by NUMA and accelerator topology reduce movement cost and avoid avoidable host↔device traffic?

H3 / SCHEDULING

Graph-aware dispatch

Can dependency readiness and deadlines improve tail latency under mixed-priority, multi-model inference?

H4 / SHARING

Capability-protected shared tensors

Can shared backing objects reduce copies while retaining strong lifetime and authority guarantees across processes?

H5 / STATE

Persistent model residency

Can OS-visible weights, adapters and KV-cache state improve cold-start, TTFT and memory reuse across workloads?

FIRST WORKLOAD

Single-host multi-model LLM inference

The first serious workload should stress memory pressure, competing deadlines, model-state residency and heterogeneous placement on one machine.

07 · Boundaries

What Nexora deliberately does not try to replace.

Scope is part of the architecture. Rebuilding mature ecosystems would obscure the actual research question and consume effort without demonstrating why AI semantics belong in the operating system.

FRAMEWORKS

PyTorch and JAX

They remain programming and execution frameworks. Nexora should consume selected semantics, not reimplement their user-facing model abstractions.

DEVICE STACKS

CUDA and ROCm

Modern accelerator drivers and compiler stacks remain external dependencies in the practical experimental path, especially for Nexora-X.

ORCHESTRATION

Kubernetes and serving systems

Cluster scheduling and service-level orchestration remain separate layers. Nexora focuses first on machine-level resource semantics.

08 · Next

The next engineering sequence is architectural, not cosmetic.

The repository is now safer and better validated, but the next useful milestone is not another numbered overlay. It is the migration from historical snapshots into one authoritative kernel source tree with end-to-end process and memory semantics.

Unify the source tree

Move the Phase 14 baseline and validated Phase 15–17 mechanisms into one maintained kernel/runtime/test hierarchy while keeping historical phases as archives.

Implement process virtual memory

Build real address-space creation, ELF segment mapping, user stacks, teardown and rollback instead of relying on abstract host-test mapping callbacks.

Add reference-counted kernel objects

Introduce a lifetime model that makes capability delegation, shared tensors and multi-process resource ownership safe by construction.

Back NXTensor with real storage

Connect tensor metadata to physical frames or device-backed memory and expose controlled user mappings rather than descriptor pointers.

Build runnable process scheduling

Replace fault-time fail-stop behavior with process termination, scheduler handoff and return to another runnable context.

Then bring up SMP

Add AP startup, per-CPU structures, locking/lock-free policies and interrupt-safe observability only after the single-core invariants are coherent.
