NEXORA

An AI-native operating-system research architecture in which tensor lifetimes, work graphs, topology, state, deadlines, and capabilities become visible to the resource manager instead of being hidden behind conventional process and page abstractions.

Research position

Nexora is not a replacement for PyTorch, CUDA, ROCm, PJRT, or Linux today. It is a testable systems hypothesis: expose enough AI semantics to the operating system to improve whole-machine scheduling, memory placement, isolation, and data movement.

01 · THESIS

The operating system should see the shape of the work.

AI applications already know which objects are model weights, activations, KV cache, temporary workspace, or persistent state. They know dependency graphs, deadlines, and accelerator preferences. Nexora asks whether some of that information should cross the kernel boundary and participate directly in resource management.

Object 01

Tensor semantics

Typed shape, lifetime, placement class, ownership, reuse hints, and eventually real backing storage.

Object 02

Work graphs

Dependencies become explicit scheduling information rather than a sequence of opaque, unrelated calls.

Object 03

Capability authority

Resource access is represented as explicit rights over kernel objects, with constrained delegation.

02 · ARCHITECTURE

Semantic policy above mechanical execution.

Nexora separates what the system knows about AI work from the low-level mechanisms that execute it. The distinction is deliberate: policies should evolve without rewriting the kernel substrate.

03 · PRIMITIVES

Eight concepts define the research vocabulary.

The vocabulary is intentionally small. Every primitive must earn its place by enabling a measurable systems experiment.

NXTensor

Semantic data object

Describes typed multidimensional data, location class, lifetime, mutability, and ownership.

NXWork

Schedulable semantic unit

Represents an operation with inputs, outputs, priority, deadline, and device constraints.

NXGraph

Dependency structure

Makes readiness, downstream reuse, and reclamation opportunities explicit.

NXState

Persistent AI state

Models weights, KV cache, adapters, session state, and other long-lived resources.

NXResource

Unified resource description

Provides a common model for compute, memory, storage, and network resources.

NXTopology

Movement cost map

Represents locality, bandwidth, latency, NUMA distance, and accelerator interconnects.

NXCapability

Explicit authority

Defines who may use which resource, with which rights and constraints.

NXScheduler

Semantic placement policy

Combines graph state, locality, resource pressure, deadlines, and permissions.

05 · LIMITS

Research credibility depends on stating what is not built.

Nexora deliberately narrows its claims. The following boundaries remain active until code and executable validation remove them.

CPU

No SMP claim

v0.1 runs with one virtual CPU while per-CPU ownership and synchronization are designed.

Memory

No user tensor mapping yet

The mapping syscall returns ENOSYS rather than exposing a kernel pointer without a real VM layer.

Accelerators

No real GPU/NPU execution

Device classes exist as semantic abstractions; hardware execution backends remain future work.

Scheduling

Synchronous executor

The current executor is deterministic and graph-aware, but not yet preemptive or asynchronously device-driven.

Time

No fabricated timing

Result timestamps remain zero until a calibrated monotonic kernel clock is wired.

Allocator

Object reuse, not page return

Slabs reuse objects; fully free slab pages are not yet reclaimed to the frame allocator.

06 · PROGRAM

The next proof should be quantitative.

The project should advance by experiments, not feature count: first a monotonic clock and VM-backed tensor storage, then asynchronous simulated accelerators, locality-aware placement, and only later SMP and real device backends.
