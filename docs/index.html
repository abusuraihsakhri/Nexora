Neural EXecution Orchestration and Resource Architecture

Nexora is an AI-native operating-system research project exploring whether the operating system can make better resource decisions when tensors, computation graphs, model state, topology and deadlines are visible as first-class semantics.

The central research question is not whether an operating system should replace AI frameworks. It is whether the OS can coordinate memory, placement and execution more effectively when it understands more than processes, pages and devices.

01 · Definition

What Nexora is

Nexora introduces an operating-system semantic plane beneath or alongside established AI frameworks. The project is deliberately narrower than a general-purpose Linux replacement: it concentrates on the mechanisms where AI workload knowledge could change scheduling, memory lifetime, state residency and accelerator placement.

Scope discipline. Nexora does not initially attempt to replace PyTorch, JAX, CUDA, ROCm, OpenXLA, Kubernetes or model-serving frameworks. Those systems remain valuable layers; Nexora investigates the machine-level decisions that sit below them.
02 · Primitives

Eight first-class semantics

The architecture is organized around eight objects that make AI execution intent explicit.

01 / NXTENSOR

NXTensor

Typed multidimensional data with shape, size, location, mutability, lifetime and reuse hints visible to the system.

02 / NXWORK

NXWork

A schedulable semantic operation with inputs, outputs, priority, deadline and resource constraints.

03 / NXGRAPH

NXGraph

A dependency graph that exposes readiness, lifetime boundaries and opportunities for parallel execution.

04 / NXSTATE

NXState

Persistent model resources such as weights, KV caches, adapters and session state.

05 / NXRESOURCE

NXResource

A common description of CPUs, accelerators, memory tiers, storage and network resources.

06 / NXTOPOLOGY

NXTopology

The physical and logical interconnect graph: NUMA distance, PCIe hierarchy, bandwidth and locality.

07 / NXCAPABILITY

NXCapability

Explicit authority for accessing and delegating resources, constrained by rights and object lifetime.

08 / NXSCHEDULER

NXScheduler

A scheduling model that can account for compute time, transfer cost, queue delay, pressure and deadlines.

03 · Structure

Semantic plane, mechanism plane

The design separates AI-specific meaning from low-level kernel mechanism. This keeps the experimental hypothesis legible: semantic policy may evolve without pretending that ordinary paging, interrupts and privilege boundaries disappear.

04 · Ledger

Implementation status

The repository contains historical phase snapshots. The status below distinguishes code that forms the current integrated research-kernel baseline from later validation and observability packages. This is intentionally more conservative than a marketing roadmap.

Phases 01–14
Integrated kernel lineage

Boot, allocators, AI metadata/work graph, privilege structures, syscall/ELF validation and host-side integration tests. Phase 14 is the last complete kernel tree in the historical layout.

Phase 15
Benchmark tooling

JSONL benchmark schema, summaries and threshold-based regression gates. Useful measurement infrastructure; not itself a kernel feature.

Phase 16
Validation overlay

Telemetry, deterministic fault injection and release-health tooling. CI validates this package independently while kernel integration is treated as explicit work, not implied.

Phase 17
Release discipline

Health, trace, watchdog and release-gate mechanisms. The repository-wide CI now executes its gate from the correct root workflow location and verifies a committed integrity manifest.

05 · Inquiry

Research hypotheses

Each claim is framed as something to measure rather than something already proven.

H1

Semantic tensor lifetime

Can producer/consumer knowledge reduce peak memory by reclaiming intermediates earlier than lifetime-blind allocation?

H2

Locality-aware placement

Can topology-aware decisions reduce host↔device and device↔device transfer cost?

H3

Graph-aware scheduling

Can dependency-aware dispatch improve tail latency under mixed-priority inference load?

H4

Shared tensor handles

Can capability-protected backing objects reduce duplication without weakening isolation? This requires correct lifetime accounting before enablement.

H5

Persistent model state

Can OS-visible model and KV-cache residency reduce cold-start and time-to-first-token?

TARGET

Single-host multi-model inference

The first target workload is concurrent LLM inference on a heterogeneous machine under memory pressure.

06 · Method

Four questions for every mechanism

Architectural additions should earn their complexity with an explicit systems argument and a measurable result.

Problem. What concrete limitation in existing systems is being addressed?
Layer. Why is the operating system the right place to act, rather than a runtime or framework?
Mechanism. What minimum kernel primitive is required, and what is deliberately left outside the kernel?
Metric. Which reproducible measurement would falsify or support the hypothesis?
